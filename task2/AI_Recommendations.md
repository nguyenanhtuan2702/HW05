# HW05 Task 2.3 – Backend Performance Optimization Recommendations

## Scope and evidence

This report proposes optimizations for the EShop implementation after inspecting the backend, its SQLite database, the admin UI, and the raw JMeter results. It does not modify source code or assign a final Feasible/Hallucinated judgment to any recommendation. Expected benefits are hypotheses to validate with a controlled rerun, not guaranteed outcomes.

### Verified architecture

| Area | Verified fact | Evidence |
|---|---|---|
| Backend and database | The backend uses Express 5.2.1 and `sqlite3` 6.0.1. `database.js` opens one shared `sqlite3.Database` connection. No connection-pool dependency or compression middleware dependency is declared. | [`backend/package.json`](../backend/package.json#L13), [`backend/database.js`](../backend/database.js#L1), [`backend/server.js`](../backend/server.js#L1) |
| Admin order listing | `GET /api/admin/orders` runs `SELECT orders.*, users.name ... LEFT JOIN ... ORDER BY orders.id DESC` through `db.all()` and returns the complete result set. It has no filter, pagination, or result limit. | [`backend/server.js`](../backend/server.js#L510) |
| Caching | No HTTP response cache or cache middleware was found for this route. The endpoint issues the query and returns its result on each request. | [`backend/server.js`](../backend/server.js#L510) |
| Order schema and indexes | `orders.id` is an `INTEGER PRIMARY KEY`; the source schema declares no secondary index on `orders`. A read-only inspection of the current `database.sqlite` found 2,076 orders and no secondary indexes on `orders` or `users`. `EXPLAIN QUERY PLAN` for the admin query reported a scan of `orders` and a primary-key lookup of `users`. | [`backend/database.js`](../backend/database.js#L50), [`backend/database.js`](../backend/database.js#L74) |
| Customer order listing | `GET /api/orders/my-orders` filters by `user_id` and sorts by `id DESC`. The source schema does not declare an index on `orders.user_id`. | [`backend/server.js`](../backend/server.js#L311), [`backend/database.js`](../backend/database.js#L74) |
| Order status update | The admin status endpoint selects an order's current status and then issues a separate update by `id`; both operations use the existing primary key. | [`backend/server.js`](../backend/server.js#L525) |
| Admin UI fields | The order table renders the order ID, user name, total amount, shipping address, and status. Pagination or a smaller DTO must preserve the data the UI actually uses. | [`frontend-admin/src/App.jsx`](../frontend-admin/src/App.jsx#L795) |

The database inspection was read-only and describes the database file present during this review; it is not evidence that every deployed database has identical data or schema. The admin-list query plan does not justify adding an index to that endpoint: `orders.id` is the rowid primary key, while each joined user is looked up by its primary key.

The mean Soak order-list response was about 40 times the Load mean size. The Soak file's first cited list response is 351,364 bytes and its late response is 353,304 bytes ([first](../task1/results/soak/20261121_094256/soak.jtl#L3), [late](../task1/results/soak/20261121_094256/soak.jtl#L3891)). The Spike JTL contains five successful responses above 1,000 ms: four order confirmations (1,281, 1,517, 1,292, and 1,653 ms) and one order-list/status check (1,326 ms). These occur after the observed high-concurrency sample window; the cited records show `allThreads=2` and `Connect=0`. ## Recommendations

| # | Recommendation | Problem and evidence | Source evidence | Expected benefit (to measure) | Risks and trade-offs | Preconditions and validation |
|---:|---|---|---|---|---|---|
| 1 | **Add bounded cursor pagination to the admin order list** | The endpoint returns every order. Mean response size grows from 8,706 bytes in Load to 352,330 bytes in Soak; the current database snapshot contains 2,076 orders. `db.all()` materializes the complete result set before returning it. | [`server.js:510–523`](../backend/server.js#L510); [`database.js:74–81`](../backend/database.js#L74); JTL baseline above. | Bound per-request rows, JSON serialization work, payload size, and peak result-set allocation as order history grows. A cursor based on the descending `id` ordering can avoid the growing scan cost of large offsets. | Requires updating the admin UI to request and navigate pages. A default/max page size changes the existing all-orders behavior; too-small pages can make workflows cumbersome. | Agree on page-size and navigation behavior with the UI; clamp client input and retain deterministic ordering. Compare response bytes, P95/P99, Node memory, and query plans at several table sizes. |
| 2 | **Return an explicit, minimal order-list DTO** | The SQL selects `orders.*`, which includes columns not visibly required by the admin order table. The current UI displays `id`, `user_name`, `total_amount`, `shipping_address`, and `status`; the full-file Soak mean is 352,330 response bytes. | [`server.js:513–516`](../backend/server.js#L513); [`App.jsx:795–809`](../frontend-admin/src/App.jsx#L795). | Avoid serializing and transmitting unused fields and make the response contract stable. The byte reduction may be modest compared with pagination and should be measured. | Removing a field used elsewhere in the UI or a downstream consumer can break functionality. Shipping addresses can be sensitive and should only be included where needed. | Search all consumers before changing the response shape; keep required fields and test the admin summary/actions. Measure response size and latency with representative data. |
| 3 | **Add a composite index for customer-scoped order history if that route is a target** | `GET /api/orders/my-orders` filters by `user_id`, orders by `id DESC`, and currently has no matching secondary index in the inspected database. This route was not separately measured by the supplied JTL workflow, so it is a candidate for growth, not a demonstrated bottleneck. | [`server.js:311–319`](../backend/server.js#L311); [`database.js:74–81`](../backend/database.js#L74); read-only `PRAGMA index_list(orders)` returned no secondary indexes. | An index such as `(user_id, id DESC)` may reduce scanning and sorting for a user's order history when the table grows. | Indexes add storage and write/update work. The benefit may be negligible for a small table, and it does not improve the admin list query that has no `user_id` filter. | Verify this endpoint's production traffic and run `EXPLAIN QUERY PLAN` before and after. Benchmark realistic order counts and user distributions; deploy through a migration rather than relying only on startup schema creation. |
| 4 | **Evaluate HTTP response compression for remote clients** | The Soak order-list body averages about 352 KB. The backend setup shown has no compression middleware, and `compression` is not a declared dependency. However, the Task 1 report says JMeter and the backend ran on the same host via `localhost`, so the measured latency does not establish a network-bandwidth bottleneck. | [`server.js:1–13`](../backend/server.js#L1); [`package.json:13–20`](../backend/package.json#L13); [`soak.jtl:3`](../task1/results/soak/20261121_094256/soak.jtl#L3); [Task 1 environment](../task1/23120184_HW05_Task1_Report.md#L35). | If clients are remote and the JSON compresses well, reduce transferred bytes and potentially network time. | Compression consumes CPU and may provide little benefit on localhost or after pagination. JMeter's `bytes` field is not a direct measurement of compressed on-wire traffic. | Test with representative remote-client payloads and compression negotiation. Compare actual wire bytes, CPU, throughput, and latency with compression enabled/disabled; retain only if the total result improves. |
| 5 | **Make successful status transitions a single guarded database write where practical** | The endpoint performs a status `SELECT` followed by an `UPDATE`. Four order-confirmation samples in Spike took 1,281–1,653 ms; the outliers were successful, had `Connect=0`, and occurred after the sampled peak. This is a correlation to investigate, not proof that the two SQL calls caused the delays. | [`server.js:525–566`](../backend/server.js#L525); [Spike confirmation rows 274, 278, 282–283](../task1/results/spike/20261121_091902/spike.jtl#L274). | A guarded update can remove one successful-path database operation and prevent a stale read/overwrite race during concurrent transitions. | Preserving the existing transition rules and distinguishing “not found” from “invalid transition” requires careful handling. SQLite still serializes writes; an atomic update does not guarantee a material latency improvement. | Define and test every allowed transition before changing the query. Benchmark under the same status mix and concurrency; verify response semantics, conflict handling, and update correctness. |
| 6 | **Measure SQLite queue/lock behavior before changing connection concurrency** | The backend opens one shared SQLite connection and has no pool. JTL shows no failed samples or connection time in the five late Spike outliers (`Connect=0`); it does not report SQL wait time or SQLite lock state. Adding a generic pool is not justified by these data and can complicate SQLite write contention. | [`database.js:5`](../backend/database.js#L5); [`package.json:13–20`](../backend/package.json#L13); [Spike rows 274, 278, 282–284](../task1/results/spike/20261121_091902/spike.jtl#L274). | Instrumenting database callback/queue time and SQLite busy/locked errors can determine whether a concurrency change is warranted. If reproducible lock contention is found, separately benchmark a suitable busy timeout or WAL mode; neither is assumed to help this single-connection workload. | A longer busy timeout may turn errors into longer waits and worsen tail latency. WAL changes file behavior and operational requirements; multiple connections can increase write contention. | First reproduce the tail with a sustained, controlled profile and capture DB timing, lock errors, event-loop delay, and request timing. Trial one setting at a time; do not add a pool or enable WAL without evidence and deployment review. |
| 7 | **Add request-level and resource telemetry, then repeat the Spike and Soak tests** | The five >1-second Spike samples are delayed after the observed high-concurrency window, but JTL alone cannot separate application work, SQLite wait, event-loop delay, host contention, or other causes. Task 1 also recorded Node working-set snapshots of 26,136 K at Soak minute 1 and 62,348 K at minute 10; these sparse non-JTL observations do not prove a leak or identify its cause. | [`server.js:510–566`](../backend/server.js#L510); [Spike rows 274, 278, 282–284](../task1/results/spike/20261121_091902/spike.jtl#L274); [Task 1 memory observations](../task1/23120184_HW05_Task1_Report.md#L463). | Correlated route, SQL callback, event-loop, and process-memory measurements can narrow the source of tail latency and distinguish temporary allocations from sustained growth. This is diagnostic work, not a direct latency optimization. | Instrumentation adds overhead and produces operational data that must be managed. Sparse snapshots and a short run are insufficient to establish memory stability. | Use monotonic timings and request correlation IDs; collect process RSS/heap and event-loop-delay metrics at a defined cadence. Re-run a verified sustained spike and a longer soak with the same data volume and workload, then compare aligned timelines. |

## Interpretation and limitations

- The JTLs show successful HTTP 200 samples, but successful status codes do not prove that every response is functionally correct.
- The raw JTL `bytes` values establish recorded response-body sizes; they do not prove compressed network bytes, CPU use, database time, or memory use.
- The Spike tail is a reason to instrument and reproduce, not evidence that the SQLite database, the order-list query, or the status-transition code caused it.
- The supplied JTL workflow exercises the admin order list and status transition. It does not independently establish performance for customer order history, so the proposed customer-history index must be validated separately.
- The response-size and latency scenarios are not directly interchangeable: record counts, test profiles, and payload sizes differ.
- Recommendations are proposals only. No optimization was implemented or benchmarked in this report; benefits and trade-offs require controlled before/after testing.
